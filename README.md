# PyQt coordinate transformation GUI example
 A PyQt GUI example of a program that converts geographic data from one coordinate frame to another.

## Description of program <a class="anchor" id="description"></a>

This graphical user interface, designed by Qt Designer, converts geographical X-Y-Z coordinates from one coordinate frame to another. The project is meant to provide those experimenting with PyQt and Qt Designer a template to create their own GUI for projects, while also providing a useful application that imports special functions and performs special computations. 

### Reason for developing <a class="anchor" id="reason_for_developing"></a>
I've created several GUIs to streamline my data processing work, including this one to convert time-x-y-z data from one coordinate frame to another. 

I originally created GUIs in MatLab, but desired an open source computer language, not restricted by a company's control. I started using Python for work related algorithms to process and analyze data. I then created Python GUIs to streamline data processing for more productivity. I'm sharing this data coordinate transformation example with the Github/Python community since it would have broad appeal compared to other GUI creations I've made that are more specialized.

**data_conversion** is the project folder that holds the Python project repository. I typically use the Spyder IDE for most of my projects. When one invokes **main.py**, the GUI is created, and data files can be processed. The configuration file, **dataconversion.cfg**, contains the previous settings when the program was used, so that the values from the previous session will populate the fields when the application is reopened. 

Running **build.py** will compile the PyQt code that creates the graphical user interface; this needs to be only done after any GUI graphics have been changed. The folder **ui_data_conversion** contains the GUI file generated by **Qt Designer**, **mainwindow.ui**. When this file is run by **build.py**, **mainwindow.py** is created. Both input and output data are in the data folder, as seen the list of files, e.g., ***balloon_launch.lle*** (an input file), ***balloon_launch-lle.llh*** (an output file), etc. The proj directory contains the geoid undulation data file, egm08_25.gtx, that will provide the value of the undulation (above mean sea level) in height above ellipsoid (HAE) at a particular latitude and longitude. 

The extra modules and coordinate transformation algorithms are in two files, **coordinate_transformation_class.py** and **extras_class.py** in the folder **shared_modules**, at the same file heirarchy as any other Python projects are at. This way the modules can be shared among any other Python programs that require them.

### Program operation <a class="anchor" id="program_operation"></a>
Once the program is functional, it allows one to select an input file with the **Menu** selection at the upper left of the GUI. When a file is selected, the file name will appear in the **Input File to Process** text field, along with the working directory in the **Working Directory** text field. Then one should select the radio-button of the type the input file is, e.g., ***Latitude-Longitude-HAE (LLH)***. 

Next, the **Output File Type** that is desired is selected, e.g., ***Latitude-Longitude-Elev (LLE)***. The **Process** button is selected, and the input file is processed, creating the output file in the same directory. 

In this example, as shown in Figure 1, a file with time, latitude, longitude, and height above ellipsoid (HAE) values is converted into a similar file with time, latitude, longitude, and height above mean sea level (AMSL) values. The times are generally in seconds, the latitudes and longitudes are in degrees, and the height or elevation values are in meters. 

The input file *.llh: 

	time     latitude(deg)     longitude(deg)     HAE(m)
	  0        34.583672		-115.875719		  233.000
	  2		   34.583583		-115.875607		  239.141
	  4		   34.583493		-115.875495		  245.282
  ...

generates output file *.lle: 

     time  latitude(deg) longitude(deg)   HAE(m)
     0.000   34.583672    -115.875719     201.036
     2.000   34.583583    -115.875607     207.177
     4.000   34.583493    -115.875495     213.318
	 ...

Note how the latitudes and longitudes are unchanged, but the heights are, since the level of the ellipsoid at those coordinates is above the geoid by about 30 meters, or 100 feet. 

Other transforms are available, including ECEF E-F-G, which is a transformation to Cartesian coordinates from the center of the Earth: E is the axis towards the Grenwich Meridian at the equator; F is towards the 90<sup>0</sup> meridian at the equator, and G is towards the north pole. 

Also, KML (Keyhole Markup Language) files can be generated from either LLH or LLE input files; the generated KML files can be input into a GIS program to plot the path of the geographic data points. 

The local E-N-U (east-north-up) coordinate frame references a local origin with coordinates east, north, and up in meters from the origin. The geographical coordinates of the origin must be specified, as is possible from the **Input Reference Frame** and **Output Reference Frame** combination boxes. 

Note how when an input category is selected, certain output selections are grayed-out, see Figure 2. This added feature prevents one from selecting an input-output pair that has no corresponding algorithm to allow processing. Also, when an input category is selected, the corresponding output category on the GUI is grayed-out, since this would only return the same data file. 

Note as well that unless the input **ENU** option is selected, the **Input Reference Frame** combination box is grayed-out, and unless the output **ENU** option is selected, the **Output Reference Frame** combination box is grayed-out.

### Program description <a class="anchor" id="program_description"></a>
Here is a description of the inner workings of the program.

#### Qt Designer <a class="anchor" id="qt_designer"></a>
**Qt Designer**, a WYSIWYG Python GUI creator that allows manipulation of PyQt code to design very useful GUIs for a variety of applications. I have used Qt Designer for all my Python GUIs that help me process data in a streamlined manner. 

The current designer layout for the coordinate conversion program is shown in Figure 3. Among the widgets, one can see a menu, text-boxes, radio-buttons, check-boxes, combination boxes with choices, and a push-button. Within Qt Designer these widgets can be moved around, copies made and put elsewhere, and the their properties changed,or more widgets added by the toolbar on the left. 

When a particular widget is selected from the Designer GUI, the properties are displayed at the **Object Inspector** panel, as well as the **Property Editor** panel below it. Widget characteristics can be changed, such as text, font size and color, and position. Widgets are labeled so as to link them to the Python program in a signal-to-slot manner, e.g., ***radBtnOutputKML***, the radio-button that selects the output as KML. 

**QT Designer** creates an XML file, **mainwindow.ui**, that is then compiled within the Python IDE to create the file that generates the interactive GUI, **mainwindow.py**.

#### Python program <a class="anchor" id="python_program"></a>
Running the **build.py** program, shown below, in the project root directory **data_conversion** compiles the **mainwindow.ui** XML file to create a Python file, **mainwindow.py**:

**build.py** code:
    # Build qtpy project designed by Designer. 
    from qtpy import uic
    # User Interface Compiler.
    uic.compileUiDir("ui_data_conversion")

The contents of **mainwindow.py** are imported into the **main.py** program, shown in this code:

    # Import graphics generated by QtPy program. 
    from ui_data_conversion.mainwindow import Ui_MainWindow

Next, the GUI is configured. Various modules are imported into the program. **Pandas** is used to import the local east-north-up coordinate table for input and output reference frames. **rasterio** is used to read the EGM database file for geoid undulation determination. 

**module_dir** and **ultra_module_dir** are paths to higher level directories that are appended to the system path so that custom modules from the files **coordinate_transform_class.py** and **extras.py** can be imported by the program. I keep these in a sister folder to my other Python projects called **shared_modules** that is shared by all my Python programs, so that I only need one copy of the modules for all my Python programs. 

The coordinate transformations are class structured, so that I import all the coordinate transformation methods by the command: 

    from coordinate_transform_class import Transform as xfrm

Access to a class method is by **xfrm**, e.g., ***xfrm.llh2lle***. 

The **extra** functions are merely imported individually, i.e.:

**from extras import sec2HMS, kml_rkt_header, kml_dot_array, kml_placemark**

The **mainWindow** class is then built, and the various widgets from PyQt are accepted into the GUI in a signal-to-slot configuration. The menu selection that allows finding the input file is configured, as are all the text-boxes, radio-buttons, check-boxes, combination boxes, and finally the process-button to run the program. 

Next, the various radio-buttons are configured in functions that relate the input and output choices to each other. If a particular radio-button is selected, the corresponding function is called, e.g., when the ***InputENU*** button is selected, function ***set_input_file_type_enu*** is called. 

The configuration file, **dataconversion.cfg**, in the main directory is read. All the values from the previous session are loaded; this allows one to not reenter previous session values. If a configuration file is not found, it is created. 

Some variables need to be shared across the functions; **global** does this, e.g., ***global filepath, trackpoint_size***. Also if the variable is assigned as a class member, it can be globally shared. In the various input and output functions, e.g., ***def set_input_file_type_llh(self):***, if the function is selected, it is shared globally, e.g., ***xfrm.input_file_type = "llh"***.

Also configured are the radio-button selection possibilities. If the input file type selected is ***LLH***, then several others are enabled, such as:

    ***self.ui_data_conversion.radBtnOutputLLE.setEnabled(True)***
    
but others are not: 

    ***self.ui_data_conversion.radBtnOutputLLH.setEnabled(False)***
    ***self.ui_data_conversion.boxInputRefFrame.setEnabled(False)***

This is so that a user can't select a choice that has no corresponding algorithm in the GUI, and furthermore, the same output for the input is not allowed; there is no reason to create an output file with the same data as the input file, e.g., no reason to create a LLH (latitude-longitude-HAE) file from the same LLH file. If a particular radio-button or combination box is set to **False**, it will appear grayed-out in the GUI and can't be selected. 

The **in_selectionchange** and **out_selectionchange** functions read the corresponding combination boxes for local east-north-up coordinate origins. 

The **file_open** function determines the input file path from the working directory and input file. Finally, the **onProcessClick** function begins the processing. Within this function the output file name is created from the input and output file-type choices. For example, if the input file is  ***data.llh***, in the format latitude-longitude-HAE, and the output file-type desired is latitude-longitude-elevation (LLE), the output file will be named ***data-llh.lle***. The input file extension is appended to the root name, and the new file-type becomes the extension. This is to keep track of the coordinate transformations, that might be several for a particular file. 

Before other computations occur, the values in the text-boxes and radio-buttons and check-boxes are written to the configuration file, **configuration.cfg**, as information for the next session. Storing the values before major computations saves the values before any anomaly or crash might happen. 

Next, if either **input_file_type** or **input_file_type** is east-north-up (ENU), the appropriate origin values are obtained for local coordinate frame transformations. Then the input file and output files are opened, and a header line is written to the output file; this labels the data columns for easier interpretation by the data processor or anyone who might inspect the output file later. 

The time of the first data line is stored for later computation of the duration of the data. If a KML file is generated, the KML header and a special dot-list is first written to the file. The dot-list allows for multiple colored extruded trackpoint dots to represent a path or trajectory. If the input file is a rocket trajectory with the stage number as the fifth column, the individual stages will have different colors. 

Each line's time, x, y, and z component is read, and then the appropriated algorithm computes the output file data. The choices of input data types to output file-type selections is listed here: 

Note: <n>**dark blue**</n> indicates input file choices, while plain text are output file choices allowed for the particular input choice.

- #### <n>latitude-longitude-HAE (LLH)</n>
    - #### latitude-longitude-elevation (LLE)
    - #### Cartesian coordinates (EFG)
    - #### Keyhole Markup Language (KML)
    - #### ECI to Earth-centered-Earth-fixed (ECEF)
    - #### local Cartesian coordinates (ENU)

- #### <n>latitude-longitude-elevation (LLE)</n>
    - #### latitude-longitude-HAE (LLH)
    - #### Cartesian coordinates (EFG)
    - #### Keyhole Markup Language (KML)
    - #### ECI to Earth-centered-Earth-fixed (ECEF)
    - #### local Cartesian coordinates (ENU)

- #### <n>ECEF EFG (EFG)</n>
    - #### latitude-longitude-HAE (LLH)
    - #### latitude-longitude-elevation (LLE)
    - #### local Cartesian coordinates (ENU)

- #### <n>east-north-up (ENU)</n>
    - #### latitude-longitude-HAE (LLH)
    - #### latitude-longitude-elevation (LLE)
    - #### Cartesian coordinates (EFG)
    - #### local Cartesian coordinates (ENU)

Note that an east-north-up input file can generate an east-north-up output file since the local origin may be different between the input and output. 

When all the data is computed and written to the output file, the operation is finished; if the output file is KML, a KML ending is written to it. The duration of the data is computed and written to the **File Times** text-boxes. 

As the last lines show, the GUI window is instantiated, shown on screen, and kept open for view until the next operation.
